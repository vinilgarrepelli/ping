# PING end-to-end encryption design

**Status:** Design only. The Android scaffold, web app, relay, and cryptographic
protocol described here do **not** currently implement encryption.

## Goals and cryptographic profile

The relay transports opaque envelopes and provides ordering, fan-out, expiry,
and optional blob storage. It must not possess plaintext, room keys, private
keys, or enough metadata to impersonate a member. Use audited, maintained
libraries (preferably a standards-based MLS implementation) rather than
implementing primitives in Kotlin.

- **Identity signatures:** Ed25519 (one per installation).
- **Key agreement:** X25519.
- **Symmetric encryption:** ChaCha20-Poly1305 or AES-256-GCM; select one
  library-wide and never substitute unauthenticated encryption.
- **Derivation:** HKDF-SHA-256 with domain-separated labels.
- **Group protocol:** MLS (RFC 9420) with a ciphersuite supported by the
  selected library. MLS supplies authenticated membership changes, epochs, and
  forward secrecy/post-compromise recovery.

## Anonymous device identity

On first run, the device creates a random Ed25519 identity key and an X25519
identity/agreement key. Keys are generated locally from the platform CSPRNG;
the server never generates or receives private material. The public identity
key (or a stable, server-assigned opaque hash of it) is the account/device
identifier. No phone number, address book, or user name is required by this
protocol. A user may add an application-level display name, but it is not an
authentication factor.

The device publishes the identity public key, signed prekey, and a bounded
set of one-time prekeys. A prekey bundle is signed by the Ed25519 identity.
Prekeys are replenished before exhaustion and are never reused after a
successful initial handshake.

## Joining a room and authenticating members

1. The inviter obtains the candidate's signed prekey bundle through the relay.
2. The joining device verifies the identity signature and displays a
   short-authentication-string/QR option for out-of-band verification.
3. An X3DH-style initial exchange (ephemeral X25519 plus the signed and, when
   available, one-time prekey) derives a pairwise secret with HKDF. The
   transcript binds room ID, both identity keys, protocol version, and
   prekey identifiers.
4. Devices authenticate MLS leaf credentials with their Ed25519 identity and
   use an MLS Welcome/Commit to enter the room. Every subsequent Commit is
   signature- and transcript-authenticated.

The relay may reorder, delay, drop, or replay handshake messages; clients
reject invalid signatures, transcript mismatches, expired prekeys, and
unexpected room membership.

## Group messages

MLS derives a fresh **epoch application secret**. For each message, derive a
message key with HKDF using the epoch secret, sender leaf ID, and sender
generation/sequence. Encrypt plaintext with AEAD. The authenticated data
includes:

`version || room_id || epoch || sender_leaf_id || generation || message_id ||
content_type`

The relay receives only the room/epoch routing fields and ciphertext. Clients
maintain a replay cache and accept each `(room_id, epoch, sender, generation)`
once; bounded gaps are allowed for offline delivery, but old epochs and
messages outside the configured replay window are rejected.

## Media and voice upload envelopes

Media/audio is encrypted before upload. The sender generates a fresh random
256-bit content key (DEK) per object and a unique 96-bit nonce per AEAD
chunk/segment. Large files use independently authenticated chunks with
`object_id`, chunk index, total chunks, room ID, and epoch in AAD. The object
manifest and MIME/size metadata are themselves authenticated and should avoid
unnecessary identifying data.

The DEK is encrypted into an envelope using a key derived from the current MLS
epoch (or, for long-lived/offline objects, a deliberately retained room media
secret). The envelope includes the object ID, key version, nonce(s), algorithm,
and ciphertext hash. Clients verify the hash and AEAD tag before playback.
Voice recording segments use the same format; streaming transport must not
reuse a nonce or key across segments.

Never use a timestamp as a nonce. Nonces are generated by a CSPRNG or a
crash-safe per-key counter; a nonce must never repeat with the same key.
Keys, plaintext buffers, and decrypted DEKs are cleared as far as the
platform/library permits.

## Membership changes and key rotation

Adding, removing, or replacing a device is an authenticated MLS Commit and
creates a new epoch. The new epoch derives fresh message/media wrapping keys.
Removed members receive no Welcome for the new epoch and clients delete old
epoch secrets after the retention window, limiting future access. A member
device loss is handled as removal plus re-addition of the replacement device.
The relay cannot force a rotation: clients reject messages whose epoch is not a
valid next epoch.

For a compromised device, MLS update commits provide post-compromise recovery
after the member contributes fresh entropy. Applications should request
periodic self-updates even when membership is unchanged.

## Trust boundaries and metadata

The relay is untrusted for confidentiality and authenticity. TLS protects
transport, but TLS termination, relay logs, backups, push services, and blob
storage must all be treated as potentially observable. The relay may learn
account/device public identifiers, room routing identifiers, envelope sizes,
timing, delivery state, and IP/network metadata unless separately minimized.
It can censor or reorder traffic but cannot alter accepted ciphertext.
Push notifications contain only an opaque wake-up token; never put plaintext
or keys in notification payloads. Endpoint compromise, malicious OS/root
access, screenshots, and traffic-analysis resistance are outside this design.

## Android Keystore and local state

Identity private keys and long-term signing material are generated with and
stored as non-exportable Android Keystore keys, preferring StrongBox when
available and falling back to hardware-backed Keystore. Require user
authentication for particularly sensitive operations when product UX permits.
Keystore aliases are random and scoped to the installation; backup/restore must
exclude private keys and encrypted protocol databases unless an explicit,
reviewed recovery design is added.

MLS state, prekeys, replay windows, and encrypted cached content live in
private app storage. Any database-encryption key is generated randomly and
wrapped by a Keystore key. On logout or device removal, wipe cached plaintext,
retire protocol state, revoke prekeys, and delete the relevant Keystore
aliases. Do not log keys, plaintext, full envelopes, or authentication
secrets.

## Implementation boundary

**Not implemented:** identity/prekey generation, X3DH or MLS, member
authentication UI/QR verification, group epochs/rotation, message or media
AEAD, replay persistence, encrypted media HTTP endpoints, secure push payloads,
Keystore integration, backup policy, deletion/wipe behavior, and cryptographic
tests/interoperability vectors. The current `MainActivity.kt` remains a visual
scaffold only. Implementation must first select and review a maintained
cryptographic/MLS library, define a versioned wire schema, and add negative,
replay, rotation, crash-recovery, and cross-device tests before claiming E2EE.

## Current relay boundary (version 1)

`server.js` exposes a separate Socket.IO surface for the Android client:

- `e2ee:join` accepts `{ version: 1, roomId, deviceId }`, where the identifiers
  are bounded strings. It places the socket in an isolated E2EE room.
- `e2ee:envelope` accepts a bounded envelope containing
  `{ version: 1, roomId, senderId, messageId, ciphertext }` and an optional
  bounded `aad` string. The routing fields must match the preceding join.
  The server emits the exact received object to the other sockets in that
  E2EE room and does not decode, authenticate, persist, or rewrite it.

This is only an opaque transport boundary, not cryptography or authentication.
The relay can observe routing fields, sizes, timing, and ciphertext, and can
drop, delay, replay, or reorder envelopes. Clients must implement and verify
the selected audited protocol, keys, membership, epochs, replay handling, and
encrypted media before calling the product end-to-end encrypted.
